# 接口设计结项报告

## 1. 设计目标与整体风格
本项目的接口遵循 RESTful 风格，以资源（orders、member 等）为中心，通过标准 HTTP 动词描述业务语义：POST 创建订单、GET 查询订单及会员资料、PUT 完成或取消订单、POST 退款等。统一使用 `/api` 前缀承载业务接口，辅以一致的 JSON 请求/响应格式，便于前后端分工与调试。接口设计优先满足以下目标：

- **清晰一致**：路径、方法、返回体保持统一命名与结构，降低认知成本。
- **安全可信**：结合 JWT 与 `X-User-Id` 头部解析用户身份，保证积分、订单等敏感操作具备来源约束。
- **扩展弹性**：预留支付、优惠、积分等可扩展字段，配合 Flyway 迁移保障向后兼容。
- **幂等与校验**：关键写操作在服务层做参数校验、金额与积分重算，防止前端篡改或重复提交导致脏数据。

## 2. 典型接口示例：创建订单
### 2.1 路径与方法
- **路径**：`POST /api/orders`
- **控制器**：`OrderController#createOrder`
- **鉴权**：优先读取请求体中的 `userId`，若缺省则尝试从 `X-User-Id` 头自动回填，保障订单必然绑定会员。

### 2.2 请求示例
```json
{
  "customerName": "张三",
  "customerPhone": "13800000000",
  "deliveryType": "pickup",
  "goodsAmount": 20.00,
  "pointsUsed": 300,
  "pointsDiscountAmount": 3.00,
  "totalAmount": 17.00,
  "items": [
    {
      "productId": 1,
      "productName": "香草拿铁咖啡",
      "price": 20.00,
      "quantity": 1,
      "subtotal": 20.00
    }
  ]
}
```

### 2.3 服务端核心流程
1. **用户解析**：控制器尝试从请求体或 `X-User-Id` 头解析用户并回填订单 DTO，确保订单关联会员（详见 `OrderController`）。
2. **价格与折扣重算**：服务层对商品小计、总价、优惠、积分抵扣进行后端重算，若与前端值不一致以服务端计算为准，防止篡改。
3. **库存与订单项**：为每个订单项落库，扣减对应商品库存（有库存约束时）。
4. **积分结算**：
   - **抵扣**：校验 `pointsUsed` 不超过可用积分；按规则 (`redeemPoints` / `redeemYuan`) 计算抵扣金额；更新订单的 `pointsDiscountAmount`。
   - **发放**：依据实付金额和活跃规则的 `earnPerYuan`（缺省 10 分/元）计算 `earnedPoints`。
   - **余额更新**：成长积分 `levelPoints` 只增不减，可用积分 `availablePoints` = 旧可用 - 使用 + 获得，并同步旧的 `points` 字段以保持兼容。
5. **状态与时间戳**：下单即视为已支付，填充 `payStatus=PAID`、`paymentTime` 等字段。
6. **持久化与返回**：保存订单、订单项与商品库存变更，返回订单 DTO（含 `usedPoints`、`pointsDiscountAmount`、`earnedPoints` 等字段）。

### 2.4 错误处理与并发
- 积分不足会抛出业务异常并回滚事务，防止负数积分。
- 价格/抵扣重算后再写库，规避重复请求或恶意篡改。
- 事务边界覆盖订单持久化、库存扣减与积分更新，确保数据一致性。

### 2.5 扩展性考虑
- 订单表预留 `couponId`、`promotionId`、`userCouponId`、`userOpenid` 等字段，便于后续接入优惠券、活动与小程序身份。
- 使用 Flyway 迁移（V18-V22 等）为老库补齐 `user_id`、`points_used`、`points_discount_amount`、`earned_points` 等列并设置默认值，保障升级平滑。

## 3. 会员资料接口
- **路径**：`GET /api/member/me`
- **控制器**：`MemberController#getProfile`
- **功能**：
  - 解析 `X-User-Id` 或 JWT 中的 `Admin` 作为认证主体，缺失则返回 401。
  - 聚合返回当前用户积分/等级、积分规则、等级列表，一次请求即可渲染会员中心。
- **返回示例**：
```json
{
  "user": {
    "id": 1,
    "points": 150,
    "levelPoints": 150,
    "availablePoints": 150,
    "level": "普通",
    "nextLevel": "黄金",
    "nextLevelMinPoints": 2000
  },
  "rules": {"earnPerYuan": 10, "redeemPoints": 100, "redeemYuan": 1},
  "levels": [
    {"name": "普通", "minPoints": 0},
    {"name": "黄金", "minPoints": 2000}
  ]
}
```
- **计算逻辑**：
  - `levelPoints` 与 `availablePoints` 从 `Admin` 记录中读取，若历史数据缺失回落到旧字段 `points`。
  - 当前等级取满足 `minPoints` 条件的最大等级；下一等级取大于当前积分的最小等级。
  - 日志记录用户 ID、当前与下一级信息，便于排查。

## 4. 数据模型与字段说明
- **Admin（会员）**：`availablePoints`、`levelPoints`、`points`（兼容字段）。
- **Order**：
  - 用户绑定：`userId`、`userOpenid`
  - 金额相关：`goodsAmount`、`discountAmount`、`couponDiscountAmount`、`totalAmount`
  - 积分相关：`pointsUsed`、`pointsDiscountAmount`、`earnedPoints`
  - 状态时间：`payStatus`、`paymentTime`、`confirmedTime`、`completedTime`、`cancelledTime`
- **积分规则**：`earnPerYuan`（元→积分倍率）、`redeemPoints` / `redeemYuan`（抵扣比例）。
- **等级**：`member_level` 中保存 `minPoints`、`sortOrder`、权益信息。

## 5. 积分与价格计算策略
1. **抵扣顺序**：先计算商品小计，再扣满减/优惠券，再按积分抵扣，保证用户利益最大化且金额不为负。
2. **积分上限**：抵扣使用的积分不能超过当前可用积分；计算出的抵扣金额向下取整到规则分组。
3. **成长与可用分离**：成长积分只增不减，用于等级判定；可用积分在抵扣时扣减，在支付时增加。
4. **后端为准**：前端传入的 `pointsUsed`、`pointsDiscountAmount`、`totalAmount` 仅作参考，后端重算后覆盖。
5. **缺省规则**：若未配置规则，发放积分默认 10 分/元，抵扣则视为 0。

## 6. 安全与鉴权
- 认证：支持 JWT 与 `X-User-Id` 混合解析，未解析到用户时敏感接口返回 401。
- 授权：订单创建依赖用户身份；会员资料接口限制未登录访问。
- 防篡改：金额与积分均由后端重算；积分不足直接拒绝。

## 7. 错误处理与返回规范
- 通常返回 4xx 提示业务错误（如积分不足、订单状态不允许操作），5xx 处理未知异常。
- 订单创建过程若出现校验失败会抛出异常并回滚事务，前端收到 4xx/5xx 后结合统一提示文案即可。

## 8. 日志与可观测性
- 会员资料接口记录用户 ID、成长/可用积分、当前/下一等级。
- 订单创建在价格与积分重算后统一持久化，异常会在日志中体现 SQL 或业务校验信息，便于排查。

## 9. 迁移与兼容
- 通过 Flyway 管理版本化迁移，逐步为历史数据库补齐用户、积分相关字段并回填默认值，保证新老环境一致。
- 服务层兼容旧字段（`points`），确保老数据在未完全迁移时仍可正常计算。

## 10. 接口规范与约定
- **统一前缀与版本**：当前接口全部挂载在 `/api` 之下，后续若需要大版本变更，可通过 `/api/v2` 并行发布实现平滑升级。
- **请求与响应格式**：请求体使用 JSON，响应体默认 `application/json`；文件导出采用 `octet-stream`，并设置合适的 Content-Disposition 头便于浏览器下载。
- **时间与货币**：时间字段统一使用 ISO-8601 本地时间字符串；货币字段使用 `BigDecimal` 存储与传输，避免浮点误差。
- **分页与排序**：列表接口（如订单查询）支持分页参数与排序字段，避免一次性返回超大数据集。

## 11. 状态码与错误语义
- **200/201**：成功返回业务数据或创建成功。
- **400**：请求参数校验不通过，例如数量为 0、积分超出可用余额、订单状态不允许操作。
- **401**：缺少或解析不到用户身份（会员资料、积分结算等敏感接口）。
- **403**：身份存在但无权限（如未来增加的店铺或角色限制）。
- **404**：资源不存在（订单、用户、商品）。
- **409**：并发或业务冲突（重复提交、库存不足）。
- **500**：未捕获的服务端异常。

## 12. 事务边界与幂等策略
- **事务覆盖范围**：创建订单时的订单保存、订单项保存、库存扣减、积分增减在同一事务内完成，任意一步失败都会整体回滚，防止部分成功导致数据错位。
- **幂等设计**：
  - 金额、积分一律由后端重算并覆盖前端提交值，天然具备幂等性。
  - 订单号以时间戳生成，若需要更严格的防重可追加业务幂等键（如前端生成的 requestId）。
  - 积分抵扣校验使用当前可用积分快照，避免重复扣减。

## 13. 安全加固与数据保护
- **身份来源复合**：订单与会员接口同时支持 JWT 与 `X-User-Id`，便于在小程序、Web 管理端共用后端。若两者同时存在，以请求体/头明确传入的用户优先，确保预期绑定。
- **最小权限**：未来可在 Security 配置中收紧 `/api/orders` 的权限，区分管理员与终端用户，避免匿名刷单。
- **输入校验**：对数量、金额、积分等关键字段做下限校验（不得为负），避免 SQL 错误或积分被刷。
- **日志脱敏**：日志仅记录用户 ID 与关键数值，不输出密码等敏感信息；如需打印手机号需做部分掩码。

## 14. 性能优化与扩展路线
- **读缓存**：积分规则、等级列表变更频率低，可在服务层做短时缓存或基于 Spring Cache 减少数据库查询。
- **批量接口**：已提供批量确认订单接口 `/api/orders/batch-confirm`，后续可按需补充批量发货、批量退款等，降低网络往返次数。
- **导出与异步化**：现有导出为简化 CSV，同步输出。若订单量增大，可改为异步任务 + 轮询查询下载链接，并使用流式写入减少内存占用。
- **横向扩展**：接口无状态，可通过容器/微服务水平扩容；订单号生成无需中心化依赖，适合分布式部署。

## 15. 兼容与演进策略
- **字段演进**：新增的 `pointsUsed`、`pointsDiscountAmount`、`earnedPoints`、`userId` 均设置默认值并在迁移中回填，确保旧数据不阻断应用启动。
- **服务兼容**：服务层在读取积分时回退到旧字段，允许逐步淘汰旧字段而不中断业务。
- **前端适配**：即使前端未传积分相关字段，后台会填充默认值并进行结算，避免前端升级不及时导致故障。

## 16. 测试与验证建议
- **单元测试**：针对积分抵扣、积分不足、价格重算、用户缺失、库存扣减等关键分支编写用例。
- **集成测试**：模拟下单→查询会员→再次下单的完整链路，验证成长积分只增不减、可用积分随抵扣而减少。
- **迁移验证**：在含历史数据的库上跑 Flyway，检查新列默认值、回填逻辑是否正确，并验证应用启动成功。
- **压测与监控**：对高频下单场景做压测，关注数据库连接池、事务耗时；上线后观察日志与监控，确保无异常堆积。

## 17. 前后端协同要点
- 前端在提交订单时带上 `X-User-Id` 或登录态，避免匿名请求导致 401/403。
- 积分抵扣与应付金额以后台回传为准，前端仅展示后台计算结果，避免因本地计算误差导致下单失败。
- 下单成功后应重新调用 `/api/member/me` 同步最新积分与等级，确保展示与后台一致。

## 18. 结论与价值
本接口体系在设计上兼顾“正确性、扩展性、易用性”三要素：
- **正确性**：后端重算金额与积分、事务保护、积分余额校验保证账实一致。
- **扩展性**：字段和迁移预留了优惠、支付、身份渠道的拓展空间；无状态接口便于横向扩容。
- **易用性**：聚合的会员资料接口、统一的返回格式与错误语义降低前端改造成本；自动用户解析减少前端传参负担。

通过上述策略，系统已具备“下单即结算积分、抵扣不影响等级、一次拉取完整会员信息”的闭环能力，能够支撑日常运营与后续业务演进。
